# cert-lab: ESP32-C5 teaching firmware + PC test servers (course demos ep.21-22, ep.23, ep.24)

Everything here is **course-only**. The PKI and signing keys are generated by `make_pki.sh` into `demo-pki/`
(git-ignored). Never reuse them for anything real, and never use a product key here.

Hard rules for this lab: **no eFuse is burned, no Secure Boot, no flash encryption.**
`CONFIG_SECURE_BOOT` / `SECURE_BOOT_V2_ENABLED` stay OFF; images are signed with
`CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT` (ECDSA P-256, "Secure Boot v2 format" signature block verified by the
running app at OTA time; the bootloader does not check it).

```
esp32/
  make_pki.sh        lab root + intermediate, server certs (good / wrong name / rogue root), mTLS client certs, OTA keys
  https_server.py    PC lab server: /hello, /ota/latest.bin, 3 certificate flavours on 8443/8444/8445
  mosquitto.conf     mTLS-only broker config      run_broker.sh   Docker run, host port bound to the LAN IP only
  broker_check.sh    test the broker from the PC before using the board
  build_all.sh       builds every mode (build/<mode>/), collects OTA images in ota-images/
  board.sh           backup / flash / monitor / restore (the only thing that touches the board)
  cert-lab/          ESP-IDF v5.5 project, target esp32c5 (Kconfig menu "Cert Lab (course demo)")
  qemu-sb/           demo ep.25: Secure Boot v2 + flash encryption in QEMU (esp32c3, virtual eFuse file) - QEMU only, see its README
```

## 0. Facts worth knowing

* ESP32-C5 is **single core** (RISC-V): tasks are not core-pinned; the demo logic runs in FreeRTOS tasks, retries use
  `esp_timer` / backoff, nothing spins in `app_main`.
* `CONFIG_MBEDTLS_HAVE_TIME_DATE` is **off by default in ESP-IDF**: with it off, a 1970 clock or an expired
  certificate is silently accepted. `cert-lab/sdkconfig.defaults` turns it on; this is itself a lecture point.
* The board trusts exactly one root (the lab root, embedded as `cert_pem`). The public `esp_crt_bundle` is disabled.
* Signing scheme is ECDSA-V2 P-256 (the C5 also supports RSA-3072 on chip rev >= 1; ECDSA keeps the key small).

## 1. PC setup (once)

```bash
export PATH=$HOME/.espressif/python_env/idf5.5_py3.14_env/bin:$PATH   # use the python env your ESP-IDF install created
. ~/esp/esp-idf-v5.5/export.sh
cd esp32                            # inside the cloned repo
./make_pki.sh <PC_LAN_IP>            # your PC's private IP on the board's Wi-Fi ; --force regenerates (then rebuild the firmware!)
WIFI_SSID='my-ssid' WIFI_PASS='my-pass' ./build_all.sh      # credentials only land in build/_local.defaults
```
Placeholders (`CHANGE_ME_SSID`) are used when the env vars are absent; the firmware logs a loud error in that case.
The same pair can be set in `idf.py menuconfig` -> Cert Lab -> Network.
Build one mode only: `MODES="tls-check" ./build_all.sh`.

Modes (each its own `build/<mode>/`, `sdkconfig.defaults` + `cert-lab/modes/<mode>.defaults`):

| mode | demo | what it does |
|---|---|---|
| tls-check | ep.21-22 | cases E (clock 1970), B (good), C (wrong hostname), D (unknown root) in one boot |
| tls-check-nosntp | ep.21-22 | SNTP skipped: B/C/D also fail with the time error |
| mqtt-mtls / mqtt-nocert / mqtt-expired | ep.23 | client cert dev-001 / none / expired |
| ota-1.0.0 | ep.24 | base image flashed by USB; asks the server for an update at boot |
| ota-1.1.0 | ep.24 | good update (signed, self-test passes) |
| ota-1.2.0-bad | ep.24 | signed, but self-test fails -> rollback |
| ota-1.1.0-forged | ep.24 | signed with `other_key.pem` -> rejected |

## 2. BEFORE the first flash: back up the board (keep whatever firmware is on it now)

Close any other serial monitor that is using the port first.

```bash
PORT=/dev/cu.usbserial-XXXX   # find yours with: ls /dev/cu.usb*
PORT=$PORT ./board.sh backup first-dump       # prints flash_id, then asks for FLASH_SIZE
PORT=$PORT FLASH_SIZE=0x400000 ./board.sh backup first-dump   # use the size flash_id reported (4MB=0x400000, 8MB=0x800000, 16MB=0x1000000)
PORT=$PORT FLASH_SIZE=0x400000 ./board.sh backup second-dump  # second read; the two .sha256 must match
espefuse.py --chip esp32c5 -p $PORT summary > backups/efuse-before.txt   # read-only, optional record
```
The dump contains your current firmware **and its NVS (Wi-Fi/user data)**: keep `backups/` private (it is git-ignored
with the rest of the build outputs; do not publish it).

### Reverting the board to its previous firmware
```bash
PORT=$PORT ./board.sh restore backups/first-dump.bin     # esptool write_flash 0 <dump>: bootloader, table, app, NVS
```
Alternative if the original project's build tree is still around: `idf.py -p $PORT flash` there (that does not restore NVS).
The lab's partition layout (nvs 0x10000, otadata 0x16000, ota_0 0x20000, ota_1 0x1C0000) probably differs from the previous firmware's,
so always restore the **whole** dump rather than single partitions.

## 3. Demo ep.21-22: server check

PC (terminal 1): `./https_server.py` (three listeners, prints TLS handshake successes/failures from the server side;
macOS may ask to allow incoming connections for Python: allow it).
Check from the PC first: `curl --cacert demo-pki/root/lab-root.crt https://<IP>:8443/hello`.
Cert switching: `./https_server.py --single wrongname` serves the wrong-name cert on 8443.

Board:
```bash
PORT=$PORT ./board.sh flash tls-check
PORT=$PORT ./board.sh monitor tls-check      # filter: | grep CERTLAB
```
Lines to look for (**measured on the board 2026-11-17**, ESP32-C5). The board prints `ESP_ERR_HTTP_CONNECT(0x7002)` and `mbedtls_code=-0xFFFFD900` (= -0x2700 printed through a sign/format bug), not the 0x8010 shape below:
```
CERTLAB: [TIME] after boot             1970-01-01T00:00:0xZ epoch=x valid=NO
CERTLAB: ---- case E-no-time ...
CERTLAB: [TLS-FAIL] E-no-time: esp_err=ESP_ERR_HTTP_CONNECT(0x7002) mbedtls_code=-0xFFFFD900 (X509 - Certificate verification failed, ...) cert_flags=0x0200 (The certificate validity starts in the future)
CERTLAB: [TIME] before sync ... / [TIME] after sync  2026-..  valid=yes
CERTLAB: [TLS-OK] server certificate accepted; HTTP 200, body: hello from cert-lab server [good]      (case B)
CERTLAB: [TLS-FAIL] C-wrong-hostname: ... cert_flags=0x0004 (The certificate Common Name (CN) does not match with the expected CN)
CERTLAB: [TLS-FAIL] D-unknown-root:   ... cert_flags=0x0008 (The certificate is not correctly signed by the trusted CA)
CERTLAB: [RESULT] case=... TRUSTED | REJECTED
CERTLAB: [HEAP] before TLS / after TLS ...
```
With `tls-check-nosntp` expect `[TIME] LAB_SKIP_SNTP is set` and flags `0x0200` on every case (flag bits can combine).

## 4. Demo ep.23: mTLS MQTT + heap

```bash
./run_broker.sh                 # docker, eclipse-mosquitto:2, mqtts on <LAN_IP>:8883 only, require_certificate + use_identity_as_username
./broker_check.sh with-cert     # PC test: CONNACK (0), broker log shows user 'dev-001'   (verified on a Mac)
./broker_check.sh no-cert       # PC test: refused; broker log: "peer did not return a certificate"  (verified)
PORT=$PORT ./board.sh flash mqtt-mtls && PORT=$PORT ./board.sh monitor mqtt-mtls
```
Look for: `[HEAP] baseline (before mqtt init)`, `[HEAP] before TLS handshake`, `[HEAP] after TLS handshake`,
`[MQTT-OK] connected with mTLS in N ms; heap used by TLS+MQTT = N bytes`, `min_free=` in every `[HEAP]` line,
and `largest_block=`. Failure variants: flash `mqtt-nocert` (board: `[TLS-FAIL] mqtt-transport`, broker: peer did not
return a certificate), `mqtt-expired` (broker rejects; the broker, not the board, checks the client cert date).
Use `docker logs`/the foreground output of `run_broker.sh` for the broker side. Reconnect backoff 2 s .. 60 s.

## 5. Demo ep.24: signed OTA + rollback (no eFuse)

Prepare: `ls ota-images/` must show `ota-1.1.0.bin`, `ota-1.2.0-bad.bin`, `ota-1.1.0-forged.bin` (build_all.sh).
PC checks (no board): `espsecure.py signature_info_v2 ota-images/ota-1.1.0.bin` -> measured: `Public key digest for block 0: ab fc 6c …` then `Signature block 1 absent/invalid. Skipping checking next blocks.` (exit 0);
`espsecure.py verify_signature --version 2 --keyfile demo-pki/ota/lab_ota_key.pem ota-images/ota-1.1.0.bin` ok;
with `other_key.pem` it fails; the forged image verifies only with `other_key.pem`.

Board, one scenario at a time (re-flash `ota-1.0.0` between scenarios; that rewrites otadata so ota_0 runs again):
```bash
PORT=$PORT ./board.sh flash ota-1.0.0
./https_server.py --ota good      # or: bad / forged ; can switch live by typing "ota bad" on its stdin
PORT=$PORT ./board.sh monitor ota-1.0.0
```
Expected lines:
* **good**: `[BOOT] running slot=ota_0 ... version=1.0.0 state=VALID`; `[OTA] offered image: version=1.1.0`;
  `[OTA-OK] signature verified ... Rebooting`; after reboot `[BOOT] running slot=ota_1 ... version=1.1.0 state=PENDING_VERIFY`,
  `[SELFTEST] ... pass`, `[VALID] self-test passed, image marked valid`.
* **bad**: offered `1.2.0-bad`, boots in `ota_1` PENDING_VERIFY, `[SELFTEST] forced failure`, `[ROLLBACK] self-test FAILED ...`,
  reboot into `ota_0` 1.0.0 with `[ROLLBACK] last invalid slot=ota_1 version=1.2.0-bad`, then `[OTA] ... already failed its self-test: skipping`.
* **forged**: `[OTA-REJECTED] image validation/signature verification FAILED: ESP_ERR_OTA_VALIDATE_FAILED (0x1503)`
  preceded by ESP-IDF's own signature-verification error lines; slot stays `ota_0` / 1.0.0.
Measured ESP-IDF wording (forged): `esp_image: Verifying image signature...` → `secure_boot_v2: Take trusted digest key(s) from running app` → `esp_image: Secure boot signature verification failed` → `esp_image: image valid, signature bad` → `esp_ota_ops: New image failed verification`. `espsecure.py verify_signature` on a good image prints `Signature block 0 verification successful using the supplied key (ECDSA).` (then "block 1/2 invalid. Skipping.", exit 0); the forged image gives "Signature could not be verified with the provided key" (exit 2).

## 6. Build results (esp32c5, ESP-IDF v5.5)

See the table the builder printed in `build/all.out`. Signed images are padded to a

## 7. Known limits / unverified

* Measured on an ESP32-C5 (v1.0, 8MB) on 2026-11-17 (ep.21-22, ep.21-22 no-SNTP, ep.23 ×3, ep.24 good/bad/forged). Back up your board with `./board.sh backup` before flashing and restore it afterwards. MQTT retry backoff measured: 2·4·8·16·32 s.
* PC side was verified on a Mac on 127.0.0.1 (broker mTLS accept/refuse, https server three certificate flavours).
* esp-mqtt with `disable_auto_reconnect` relies on a DISCONNECTED event after a failed TLS connect to schedule the retry; confirm on the board.
* NTP needs internet (`pool.ntp.org`); change `LAB_NTP_SERVER` for a LAN-only setup.
